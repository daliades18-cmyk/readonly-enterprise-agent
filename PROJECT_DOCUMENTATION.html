SENTINEL · Read-Only Enterprise Agent

Complete Architecture, Security Invariants & System Reference Guide
Specification: Autonomy Ladder Days 1–6 & Implementation Guide (§1–§14) · Enterprise Security Compliance

1. What is the Project?

The Read-Only Enterprise Agent (codenamed SENTINEL) is a production-grade, secure, read-only AI intelligence platform designed according to the Autonomy Ladder Practitioner Guide: Building a Read-Only Enterprise Agent (Days 1–6) and Implementation Guide (§1–§14).

1.1 Core Mission & The "Safe by Construction" Principle

Most AI agents fail in regulated enterprise environments because they are granted broad read/write capabilities or rely on "prompt instructions" to prevent data leakage. SENTINEL operates on the principle of Safe by Construction:

  • Absolute Read-Only Guarantee: There are zero write, mutation, execution, or deletion endpoints or tools across the estate.
  • Cryptographic Access Control: Every incoming request must carry an RS256-signed JWT. Roles, regions, and departments are cryptographically verified and bound to caller claims.
  • In-Query Pre-Filtering: Confidential documents and database rows are filtered inside SQL queries and retrieval indexes using caller entitlements—never retrieved first and filtered later.
  • Strict Output Contract: The agent never responds with raw, unconstrained text. Every response is a strictly typed JSON object where every claim requires empirical evidence citations (min_length=1), and "I cannot answer this" is a valid, structured outcome.

1.2 The Primary Access-Control Defect Solved: The "Context Carry-Over Trap"

In conventional conversational AI, conversation turns carry forward previous responses, retrieved document chunks, and tool outputs. This creates a severe security vulnerability:

The Trap: If User 1 (e.g., a Finance Director) queries sensitive invoice or payroll data, and User 2 (e.g., an unprivileged employee) joins the shared session and asks "What was the total amount of that?", traditional agents use the prior turn's retrieved context to answer User 2, leaking privileged data.

SENTINEL's Solution: The agent never carries forward retrieved chunks, tool rows, or evidence. It carries forward only the rewritten standalone question (e.g., "What was the total amount for supplier SUP-001 open invoices in EMEA?"). Retrieval, tool permission checks, and database filters are re-executed from scratch against the current turn caller's verified claims. If User 2 lacks the finance role, they receive zero data, and the request is safely declined.

3. Core Features

  1. Follow-Up Rewriting into Standalone Questions (src/session/resolver.py): Ambiguous conversational follow-ups are rewritten into fully self-contained standalone questions using recent turns before retrieval or tool execution.
  2. Strict Two-Turn History Cap (src/session/store.py): Contextual history retrieval is strictly capped at the last two turns (history[-2:]) to prevent context degradation and drift.
  3. is_followup Pass-Through Flag (src/answer/schema.py): Callers can explicitly specify whether a request is a follow-up via is_followup: bool | None.
  4. Per-Turn Caller Identity in Session Store (src/session/schema.py): Multi-user collaborative sessions track the specific caller_identity on each turn rather than assuming a single session owner.
  5. Entitlement Isolation & The Trap Avoidance (src/answer/investigate.py): All previous chunks and tool rows are discarded between turns. Retrieval and tool permissions are re-evaluated from scratch against the current turn caller's claims.
  6. Output Contract & The 7 Honesty Behaviors (src/answer/schema.py, src/answer/synthesis.py):
    • Rule 1: Grounded claims enforcing min_length=1 on evidence.
    • Rule 2: Untrusted content attribution reported with confidence="low".
    • Rule 3: Declining for want of evidence, explicitly naming missing_sources.
    • Rule 4: Scope limits derived in code directly from claims.
    • Rule 5: Row limit truncation returning kind="partial".
    • Rule 6: Plausible hypotheses investigated and disproven listed in considered_and_rejected.
    • Rule 7: Unanswered topics explicitly recorded in unanswered.
  7. Four Import-Time Constraints on Read Tools (src/tools/spec.py): Validates extra="forbid", row limits ≤ 1000, non-empty description, and unique tool names.
  8. Real Enterprise Data Estate & Inspector (src/db/database.py, src/db/repository.py): Disk-backed SQLite (platform/estate.db) or PostgreSQL with pgvector, featuring live table inspection and audit logging.

4.2 Tech Stack Selection & Alternatives

Technology Chosen Evaluated Alternative Decisive Rationale for Selection
FastAPI + Uvicorn Flask / Django Asynchronous high-throughput, native Pydantic v2 validation integration, automatic OpenAPI documentation, and sub-millisecond route dispatching.
Pydantic v2 Marshmallow / Cerberus Rust-compiled (pydantic-core) offering 10–20x performance speedup. Native support for strict model validation (extra="forbid"), recursive schema parsing, and deterministic field serialization.
PyJWT + Cryptography Generic Auth Middleware Pinning the RS256 algorithm directly in Python prevents algorithm-switching attacks (e.g., forcing HMAC with a public key or none algorithm exploits).
SQLite + pgvector SQL Pinecone / Chroma / Weaviate External standalone vector DBs decouple metadata from business records. Storing vectors alongside documents and relational tables allows atomic in-query entitlement pre-filtering in a single SQL query.
React 18 + Vite + TS Next.js / Vue Clean single-page architecture with instant Vite HMR. Compile-time typed client matching Pydantic backend models, deployable as a static Nginx container.
OpenTelemetry SDK Custom Logging / Datadog Vendor-neutral industry standard for distributed tracing. Traces tool latencies, token consumption, and cost tracking across every turn.

5. Comprehensive Directory & File Guide

5.1 Root Files

  • Makefile: Operational build, test, and lint target shortcuts.
  • pyproject.toml: Package metadata (readonly-agent), Python >=3.11 requirements, dependencies, and pytest configuration.
  • requirements.txt: Pinned dependency list for reproducible setups.
  • run_evals.py: Standalone test and evaluation runner verifying all core requirements.

5.2 Backend Core (src/)

  • src/main.py: FastAPI application gateway exposing query, auth, data, database, and telemetry endpoints.
  • src/config.py: Configuration loader for model profiles, Keycloak URLs, and rate limits.
  • src/cli.py: Interactive CLI client for direct terminal querying.
  • Identity (src/identity/):
    • claims.py: Immutable Claims dataclass and entitlement mapping.
    • verify.py: Cryptographic JWT verification pinning RS256 algorithm.
    • mock_auth.py: RSA-2048 key generator and dev token minter.
    • passwords.py: OWASP PBKDF2-HMAC-SHA256 password hashing with 600,000 iterations.
    • users.py: User registration and authentication service.
  • Answer (src/answer/):
    • schema.py: Pydantic models for Answer, Finding, and EvidenceRef.
    • investigate.py: Central investigation orchestrator and trap eliminator.
    • plan.py: Deterministic tool and corpus planner.
    • align.py: Deterministic currency normalization, time bucketing, and entity joins.
    • synthesis.py: 7-rule honesty synthesis engine.
  • Session (src/session/):
    • schema.py: Turn schema tracking per-turn caller identity.
    • store.py: Session repository with strict 2-turn history cap.
    • resolver.py: Follow-up detector and standalone question rewriter.
  • Retrieval (src/retrieval/):
    • store.py: Vector and lexical search engine with in-query entitlement pre-filtering.
    • hybrid.py: Reciprocal Rank Fusion (RRF) hybrid retrieval with entitlement-keyed cache.
  • Tools (src/tools/):
    • spec.py: @read_tool decorator enforcing 4 import-time checks.
    • call.py: Access-controlled tool execution engine.
    • adapters/erp.py: ERP adapter for invoices, purchase orders, and revenue.
    • adapters/crm.py: CRM adapter for pipelines, org changes, and dealer status.
    • adapters/obs.py: Observability adapter for production incidents.
  • Corpus (src/corpus/):
    • schema.py: Chunk and SourceDoc data models.
    • chunker.py: Structural document chunker preserving headings and clauses.
    • pipeline.py: Path-based entitlement pipeline with idempotent content hashing.
  • Database (src/db/):
    • database.py: SQLite/PostgreSQL schema manager and dev user seeder.
    • repository.py: Access-controlled repository for documents, ERP rows, and audit logs.
  • Telemetry (src/telemetry/):
    • setup.py: OpenTelemetry tracer setup with Jaeger OTLP exporter.
    • cost.py: Per-request token and dollar cost accounting.

5.3 Frontend Application (frontend/)

  • src/App.tsx: Root application component coordinating navigation and authentication state.
  • src/api/client.ts: Typed API client with auto-refreshing bearer tokens.
  • src/hooks/useAuth.ts & useChat.ts: Authentication and conversational state hooks.

6. How to Run the Project

6.1 Local Setup

# Terminal 1: Backend API
.\.venv\Scripts\Activate.ps1
python seeds/seed.py
uvicorn src.main:app --reload --port 8000

# Terminal 2: Frontend UI
cd frontend
npm install
npm run dev
  • Frontend UI: http://localhost:5173
  • API & Swagger Docs: http://localhost:8000/docs

6.2 Running via Docker Compose

docker compose -f platform/docker-compose.yml up --build -d

6.3 Running Test & Evaluation Suites

python run_evals.py

6.4 CLI Querying

python src/cli.py "Show me open invoices for SUP-001 in EMEA" --as-user finance.lead
